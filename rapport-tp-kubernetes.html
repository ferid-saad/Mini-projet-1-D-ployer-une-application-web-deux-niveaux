📚 2. Concepts Kubernetes expliqués

Concept 1
Namespace — L'espace de travail isolé

Un Namespace est une partition virtuelle du cluster. Il permet à plusieurs équipes de coexister sans interférence.

Pourquoi l'utiliser ?Évite les conflits de noms · Applique des quotas de ressources · Facilite le contrôle des accès (RBAC) · Permet de supprimer toutes les ressources d'un projet en une commande.
apiVersion: v1
kind: Namespace
metadata:
  name: feridsaad   # Notre espace de travail dédié
Concept 2
Deployment — Le gestionnaire de Pods

Un Deployment déclare l'état souhaité : quelle image, combien de réplicas, comment faire les mises à jour. Kubernetes s'assure en permanence que cet état est respecté.

Labels (app + tier)

Étiquettes clé-valeur attachées aux Pods. Les Services les utilisent pour savoir vers quels Pods envoyer le trafic. Ils doivent être uniques entre Deployments.

Réplicas

Nombre de Pods identiques à maintenir. Si un Pod tombe, le Deployment en recrée un automatiquement. API = 3 réplicas, Frontend = 2 réplicas.

selector:
  matchLabels:
    app: api       # Le Deployment ne gère QUE les Pods portant ces labels
    tier: backend  # Différent du frontend (app: frontend, tier: web)
Concept 3
Service ClusterIP — Le routeur interne

Un Service de type ClusterIP attribue une IP virtuelle stable au groupe de Pods. Les Pods peuvent apparaître/disparaître, l'IP du Service reste la même.

Comment ça marche ?Le Service sélectionne les Pods via leurs labels. Il maintient une liste d'Endpoints (IPs des Pods sains). Kube-proxy distribue le trafic entre ces Pods (load balancing round-robin).
# api-svc — port 80 du Service redirige vers le port 9898 des Pods
spec:
  type: ClusterIP
  selector:
    app: api        # Sélectionne les Pods avec ce label
  ports:
    - port: 80       # Port côté clients
      targetPort: 9898  # Port réel du conteneur podinfo
Concept 4
DNS interne — Communiquer sans IP

CoreDNS est le serveur DNS interne de Kubernetes. Il crée automatiquement un enregistrement DNS pour chaque Service.

Nom DNS complet d'un Service :
<nom-service>.<namespace>.svc.cluster.local
→ api-svc.feridsaad.svc.cluster.local

Depuis le même namespace, api-svc suffit.
# Depuis un Pod du frontend, appeler l'API par son nom DNS :
$ kubectl exec deploy/frontend -n feridsaad -- wget -qO- http://api-svc/
{
  "hostname": "api-6cfc44d4d5-h7q4x",
  "version": "6.5.4",
  "message": "greetings from podinfo v6.5.4"
}
Concept 5
Ingress — Le point d'entrée unique

Un Ingress expose plusieurs Services sous un seul port (80/443) avec du routage par nom d'hôte (virtual hosting). Le contrôleur Ingress (ici Traefik, fourni par k3s) traduit ces règles.

CritèreNodePortIngress
PortUn port 30000-32767 par appPort 80 unique
URLhttp://IP:31234http://api.k3s.local

RoutagePar port uniquementPar hôte ET par chemin
rules:
  - host: web.k3s.local   # → frontend-svc:80
  - host: api.k3s.local   # → api-svc:80
Concept 6
Rolling Update — Mise à jour sans coupure

Le Rolling Update remplace les Pods progressivement, un par un, sans jamais supprimer tous les anciens avant que les nouveaux soient prêts.

Les deux paramètres clés :
• maxUnavailable: 0 → Jamais moins de 3 Pods disponibles pendant la mise à jour
• maxSurge: 1 → Au maximum 1 Pod supplémentaire créé temporairement

+ readinessProbe → Un Pod ne reçoit du trafic que lorsqu'il répond à /readyz
# Pendant la mise à jour 6.5.4 → 6.6.0 :
Req  1 → version: 6.5.4  ✓  # anciens Pods actifs
Req  2 → version: 6.5.4  ✓
Req  3 → version: 6.6.0  ✓  # premier nouveau Pod actif
Req  5 → version: 6.5.4  ✓  # mix des deux versions = zéro coupure
Req 17 → version: 6.6.0  ✓  # bascule finale
Req 20 → version: 6.6.0  ✓
✅ Après la mise à jour, l'ancien ReplicaSet est conservé à 0 réplica dans l'historique — permet le rollback instantané.
# Rollback vers la version précédente :
$ kubectl rollout undo deployment/api -n feridsaad
deployment.apps/api rolled back
$ kubectl rollout status deployment/api -n feridsaad
deployment "api" successfully rolled out
Concept 7
Diagnostic de panne — Méthode d'investigation

1. Vue d'ensemble

kubectl get pods -n feridsaad → Voir les Pods en erreur (Evicted, CrashLoopBackOff, ImagePullBackOff…)

2. Détail du Pod suspect

kubectl describe pod <nom> → Lire la section Events en bas (cause de l'échec)

3. Logs du conteneur

kubectl logs <pod> et --previous si le Pod a redémarré

4. Endpoints du Service

kubectl get endpoints api-svc → Si <none>, le Service ne voit aucun Pod → problème de label ou de santé

5. Corriger et vérifier

Modifier le manifeste → kubectl apply -f → kubectl rollout status

⚠️ Incident observé : Pods Evicted lors du rolling update sur VirtualBox. Cause : pression mémoire (faible RAM de la VM). Correction : maxSurge: 0 et limits mémoire réduites à 32Mi.
# Nettoyage des Pods morts :
$ kubectl delete pods --field-selector=status.phase=Failed -n feridsaad

💬 5. Réponses aux questions pédagogiques

Q0
Pourquoi isoler un projet dans un namespace ?

Le namespace crée un espace de noms virtuel isolé. Avantages : pas de conflit de noms entre équipes, quotas de ressources applicables, droits RBAC par namespace, et nettoyage simplifié (kubectl delete namespace feridsaad supprime tout).

Q1
Qui décide sur quel nœud placer les Pods ?

Le Scheduler Kubernetes (kube-scheduler) prend cette décision automatiquement en filtrant (ressources disponibles, taints) puis en scorant les nœuds (meilleure distribution, affinité). Il tend à répartir les Pods pour maximiser la disponibilité.

Q2
Que se passe-t-il si deux Deployments ont les mêmes labels ?

Le Service sélectionnerait les Pods des deux Deployments et enverrait du trafic au mauvais conteneur (nginx recevrait des requêtes destinées à podinfo). Les readinessProbes échoueraient et les Deployments se disputeraient la propriété des Pods → comportement imprévisible.

Q3
Nom DNS complet + utilité de get endpoints ?

Nom DNS : api-svc.feridsaad.svc.cluster.local (dans le même namespace : api-svc suffit).

get endpoints : Liste les IPs:ports des Pods réellement sélectionnés. Si <none>, le sélecteur du Service ne correspond à aucun Pod → diagnostic immédiat d'un problème de label.

Q4
Pourquoi Ingress plutôt que NodePort ?

L'Ingress offre un point d'entrée unique (port 80) avec routage par nom d'hôte, TLS centralisé et URL lisibles (api.k3s.local). NodePort expose un port aléatoire (30000–32767) par application, difficile à maintenir et peu sécurisé.

Q5
Combien de ReplicaSets après la mise à jour ? Pourquoi l'ancien est conservé ?

Il existe 3 ReplicaSets après la mise à jour (révisions 1, 3, 4). L'ancien est conservé à 0 réplica car Kubernetes maintient un historique (revisionHistoryLimit=10 par défaut). Cela permet le rollback instantané : kubectl rollout undo réactive l'ancien ReplicaSet sans rebuild d'image.

Q6
Quels symptômes mènent au diagnostic ? Cause racine ?

Symptômes : Pods en état Evicted dans kubectl get pods. Investigation : kubectl describe node révèle low on resource: memory. Cause racine : La VM VirtualBox dispose de peu de RAM ; le maxSurge: 1 créait un Pod supplémentaire lors du rolling update, saturant la mémoire. Correction : maxSurge: 0 + réduction des limites mémoire.

🎓 6. Difficultés et enseignements

🔴 Evictions VirtualBox

Pression mémoire lors du rolling update → Pods expulsés. Solution : maxSurge: 0 + limits mémoire à 32Mi.

🟠 Fichier hosts Windows

Droits administrateur requis. Alternative : curl.exe -H "Host: api.k3s.local" pour les tests.

🟢 DNS interne

api-svc suffit dans le même namespace. Pas d'IP à gérer — résilience automatique si un Pod change d'IP.

🔵 readinessProbe = clé du zero-downtime

Sans probe, des Pods non prêts reçoivent du trafic → erreurs 502. La probe garantit la disponibilité lors des updates.
